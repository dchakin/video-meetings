# Research: технологическая реализация загрузки файлов встречи

**План:** @docs/plan-meeting-file-upload-and-display.md
**PRD:** @docs/prd-meeting-file-upload-and-display.md
**Дата:** 2026-09-12

Цель документа — зафиксировать конкретные технические решения (библиотеки, классы, паттерны) для каждой фазы плана, с учётом текущего стека (`Nest.js 11` + `Prisma 6` на бэкенде, `Nuxt 4` + `Nuxt UI` на фронтенде) и ограничений PRD (локальная ФС, без object storage, без предпросмотра).

## 1. Хранение файлов на диске

**Директория.** Не использовать `apps/api/dist` или что-либо внутри воркспейса — при `nest build` (`deleteOutDir: true`) директория пересоздаётся и удалит файлы. Нужна отдельная директория вне дерева сборки, путь — через env (например `MEETING_FILES_DIR`, по умолчанию `./storage/meeting-files` относительно `apps/api/`, аналогично тому, как `DATABASE_URL` уже задаётся в `apps/api/.env`). Директорию добавить в `.gitignore` и в `.dockerignore` (если/когда появится Dockerfile для api) — она build-artefact и не должна коммититься.

**Имя файла на диске vs. оригинальное имя.** Хранить оригинальное имя файла только в БД (поле `originalName`), а на диске — сгенерированное уникальное имя (`uuid` + расширение или без него), чтобы избежать: коллизий одинаковых имён от разных пользователей, path traversal через оригинальное имя (`../../etc/passwd`), проблем с не-ASCII символами в имени файла на файловой системе. Это стандартный подход `multer.diskStorage`, где функция `filename` генерирует безопасное имя, а `destination` — фиксированная директория из env.

**Плоская структура vs. по встречам.** Для простоты и во избежание накопления тысяч файлов в одной директории — подкаталог на встречу: `MEETING_FILES_DIR/<meetingId>/<uuid>-<ext>`. При удалении встречи (`onDelete: Cascade` на `Meeting` уже настроен для `User`) потребуется отдельно чистить директорию на файловой системе — Prisma cascade удалит только строки в БД, не файлы. Это стоит зафиксировать как doc-задачу вне скоупа текущего плана (встречи пока не удаляются в UI), но не забыть при появлении удаления встреч.

**Лимит размера.** Задаётся через env (например `MEETING_FILE_MAX_SIZE_BYTES`) и используется в двух местах одновременно (см. §2) — на уровне `multer` (`limits.fileSize`) и, опционально, дублируется валидатором Nest (`MaxFileSizeValidator`) для единообразного формата ошибки.

## 2. Приём multipart на бэкенде (Nest.js + Multer)

Nest из коробки использует `multer` через `@nestjs/platform-express`. Рекомендуемый паттерн:

```ts
@Post(':id/files')
@UseInterceptors(
  FileInterceptor('file', {
    storage: diskStorage({
      destination: (req, file, cb) => cb(null, meetingUploadDir(req.params.id)),
      filename: (req, file, cb) => cb(null, `${randomUUID()}${extname(file.originalname)}`),
    }),
    limits: { fileSize: maxFileSizeBytes },
  }),
)
upload(
  @Param('id') id: string,
  @CurrentUser() user: JwtPayload,
  @UploadedFile(
    new ParseFilePipe({
      validators: [], // основной лимит уже на уровне multer.limits
      fileIsRequired: true,
    }),
  )
  file: Express.Multer.File,
) { ... }
```

Ключевые решения:

- **`diskStorage`, а не `memoryStorage`.** `memoryStorage` держит весь файл в `Buffer` в памяти процесса — при нескольких параллельных загрузках больших файлов это риск исчерпания памяти (именно об этом предупреждает PRD). `diskStorage` пишет поток сразу на диск, в память попадает только текущий чанк.
- **Лимит на уровне `multer.limits.fileSize`, а не только `ParseFilePipe`.** Валидатор Nest (`MaxFileSizeValidator`) проверяет размер уже полученного файла — с `diskStorage` это означает, что превышающий лимит файл **уже записан на диск** до момента проверки. Лимит `multer.limits.fileSize` останавливает поток раньше и (в актуальных версиях `multer`) сам вызывает `storage._removeFile` для недописанного файла — это и даёт требуемое PRD поведение «файл сверх лимита отклоняется... и не сохраняется на диске». Это поведение нужно подтвердить тестом на этапе реализации (unit/e2e: загрузка файла сверх лимита → в директории файла нет), а не полагаться на память о документации.
- **Обработка ошибки лимита.** При превышении `limits.fileSize` `multer` бросает `MulterError` с `code === 'LIMIT_FILE_SIZE'` — Nest по умолчанию превращает необработанное исключение в `500`. Нужен явный `exceptionFilter` (или обработка в самом контроллере/интерцепторе) на `MulterError`, чтобы вернуть `400`/`413` с понятным сообщением, как того требует PRD («понятная ошибка»).
- **Только владелец загружает.** Проверка `ownerId === user.sub` — до интерцептора не вынести (Nest выполняет `@UseGuards` раньше `@UseInterceptors`, но проверка владения встречей всё равно требует запроса к БД), поэтому логичнее: guard проверяет JWT глобально, а проверку владения конкретной встречей делает сервис/handler после того как файл уже принят диском **или** — чтобы не тратить трафик и диск на загрузку от чужого пользователя — отдельный guard/pipe, читающий `meetingId` из `params` до интерцептора. Второй вариант предпочтительнее (не пишет байты на диск от неавторизованного пользователя), реализуется как `CanActivate`, не зависящий от body.
- **Ограничение Express/Nest body-parser** на multipart не требуется отдельно настраивать — оно регулируется `multer.limits`, а не `bodyParser.json()`, так как multipart обрабатывается отдельным парсером.

## 3. Модель данных `MeetingFile` (Prisma)

```prisma
model MeetingFile {
  id           String   @id @default(uuid())
  meetingId    String
  meeting      Meeting  @relation(fields: [meetingId], references: [id], onDelete: Cascade)
  uploadedById String
  uploadedBy   User     @relation(fields: [uploadedById], references: [id])
  originalName String
  mimeType     String
  size         Int
  storagePath  String   // относительный путь на диске, не отдавать наружу как есть
  createdAt    DateTime @default(now())

  @@index([meetingId])
}
```

`storagePath` хранить относительным (от `MEETING_FILES_DIR`), не абсолютным — упрощает перенос директории между окружениями и не «зашивает» абсолютный путь хоста в БД (важно и для контейнеризации: путь на хосте и путь в контейнере могут отличаться).

`onDelete: Cascade` на `Meeting` уберёт строки `MeetingFile` из БД при удалении встречи, но **не тронет файлы на диске** — см. §1.

## 4. Модель доступа: «владелец» vs «участник»

Это главный открытый технический вопрос, который PRD прямо помечает как требующий уточнения. Текущая модель:

```prisma
model Meeting {
  ...
  participants String[]  // судя по CreateMeetingDto — просто строки, вероятно email
  ownerId      String
  owner        User      @relation(...)
}
```

`participants` — это **массив строк**, не связь с таблицей `User` (нет `participantIds`, нет промежуточной таблицы). Значит на текущий момент система не может достоверно сопоставить `participants: string[]` авторизованному пользователю, если это email, отличный от email в его `User`-записи, либо если участник вообще не зарегистрирован. Варианты для этапа реализации (эскалировать явным решением, не тихой догадкой):

1. **Простое сопоставление по email**: `participants` трактуются как email, доступ на чтение/скачивание файла даётся, если `user.email ∈ meeting.participants` (или `user.id === meeting.ownerId`). Плюс: не требует миграции `Meeting`. Минус: хрупко — при смене email доступ теряется/появляется неявно; незарегистрированные участники не имеют доступа в принципе, что и так следует из наличия JWT-гварда на всех эндпоинтах.
2. **Отдельная таблица связи `MeetingParticipant(meetingId, userId)`**, наполняемая при создании встречи по email → поиск `User` (если не найден — участник просто не получит доступа до регистрации, либо в `participants` remains как есть для отображения). Правильнее с точки зрения доменной модели, но требует миграции `Meeting`/`CreateMeetingDto` за рамками плана по файлам — вероятно избыточно для текущего скоупа.

**Рекомендация:** вариант 1 (сопоставление по email) — минимальное изменение, соответствует духу PRD «в этой фиче не трогаем модель участников глубже необходимого», и его достаточно для критерия готовности «участник может скачивать файлы». Зафиксировать это явно в задаче фазы 2 плана, а не выяснять по ходу кода.

## 5. Скачивание файла

Nest поддерживает возврат файла как потока через `StreamableFile` (`@nestjs/common`):

```ts
@Get(':id/files/:fileId/download')
async download(...): Promise<StreamableFile> {
  const meta = await this.files.getForDownload(meetingId, fileId, user);
  const stream = createReadStream(absolutePath(meta.storagePath));
  return new StreamableFile(stream, {
    type: meta.mimeType || 'application/octet-stream',
    disposition: `attachment; filename="${encodeRFC5987(meta.originalName)}"`,
  });
}
```

Важно для «побайтового совпадения» (критерий готовности): читать файл через `fs.createReadStream`, не через промежуточную буферизацию — так гарантируется точная передача байтов и низкое потребление памяти на больших файлах. `Content-Disposition` с не-ASCII именами файла требует RFC 5987-кодирования (`filename*=UTF-8''...`), иначе кириллические имена файлов будут повреждены в некоторых браузерах/клиентах — стоит проверить это отдельным e2e-кейсом, если ожидаются кириллические имена файлов.

Проверка прав — как в §4, до открытия файла (404, если встреча не найдена/нет доступа — не палить наличие файла у пользователя без прав через отличающийся код ошибки).

## 6. Удаление файла

Порядок операций важен для консистентности:

1. Прочитать запись `MeetingFile`, проверить владение (только владелец встречи).
2. Удалить строку в БД.
3. Удалить файл с диска (`fs.unlink`).

Удалять **сначала запись в БД, затем файл** — если процесс упадёт между шагами, в худшем случае останется файл-сирота на диске (не страшно, чистится отдельной задачей/скриптом при необходимости), а не битая ссылка в БД на несуществующий файл (что сломало бы скачивание для остальных участников). Обратный порядок хуже: если удаление файла с диска прошло, а запись в БД не удалилась (например, БД недоступна), список файлов продолжит показывать «файл», скачивание которого будет падать 404/500 — хуже для UX. `fs.unlink` обернуть в try/catch с логированием (не считать 500 ошибкой пользователя, если файла физически уже нет — `ENOENT` игнорировать).

## 7. Frontend: composable и загрузка с прогрессом

**Прогресс загрузки — ключевое ограничение.** `$fetch`/`ofetch` (используемые в текущем `useApi()`) построены поверх `fetch` и **не поддерживают колбэк upload-прогресса** — это известное и до сих пор не закрытое ограничение `ofetch`/Nuxt (см. issue `unjs/ofetch#45`, обсуждение `nuxt/nuxt#28063`). Единственный браузерный API, отдающий `progress`-события при загрузке (не скачивании) — `XMLHttpRequest` (`upload.onprogress`). Следствие для composable: метод загрузки файла нельзя реализовать через существующий `useApi()`/`$fetch` — нужен отдельный метод на `XMLHttpRequest`, оборачивающий тот же base URL/токен авторизации вручную (взять `token.value` из `useAuth()`, `config.public.apiBase` из `useRuntimeConfig()`, как это уже делает `useApi()`).

Набросок:

```ts
function uploadWithProgress(meetingId: string, file: File, onProgress: (pct: number) => void) {
  return new Promise<MeetingFile>((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    const form = new FormData();
    form.append('file', file);
    xhr.open('POST', `${apiBase}/meetings/${meetingId}/files`);
    xhr.setRequestHeader('Authorization', `Bearer ${token}`);
    xhr.upload.onprogress = (e) => e.lengthComputable && onProgress((e.loaded / e.total) * 100);
    xhr.onload = () => (xhr.status < 300 ? resolve(JSON.parse(xhr.responseText)) : reject(...));
    xhr.onerror = () => reject(...);
    xhr.send(form);
  });
}
```

Остальные методы composable (`list`, `remove`, `downloadUrl`) можно оставить на `useApi()`/`$fetch` — прогресс нужен только для загрузки.

**Скачивание** — не через `$fetch` (не нужно грузить файл в память вкладки ради скачивания): либо прямая ссылка `<a :href download>` на `GET /meetings/:id/files/:fileId/download` с токеном через query-параметр или cookie (JWT сейчас, судя по `useAuth`, скорее всего не в httpOnly cookie, а в обычной cookie/сторе — уточнить на этапе реализации, как передать `Authorization` заголовок без `$fetch`, поскольку обычная ссылка не может выставить кастомный заголовок), либо программный `fetch`/`XMLHttpRequest` + `Blob` + временная ссылка на скачивание. Нужно решить на этапе реализации, как именно проксировать авторизацию для прямых ссылок (частый паттерн — короткоживущий подписанный URL или query-параметр `?token=`, если он допустим по требованиям безопасности проекта).

**UI-компонент.** Nuxt UI (используемая версия судя по `app/CLAUDE.md`) уже имеет готовый компонент `UFileUpload` с `dropzone` (drag-and-drop включён по умолчанию) и `multiple` — не нужно писать drag-and-drop руками. Это закрывает большую часть требований фазы 4 плана «из коробки»; поверх него — свой прогресс-бар (`UProgress`) и список файлов (`UTable`/список карточек), управляемые локальным состоянием composable.

## 8. Тестирование

- **Unit (api).** `fs`/`multer` не мокать глубоко — тестировать сервис уровня БД-логики (проверка владения, формирование `storagePath`) с замоканным `PrismaService`, как это уже сделано для `MeetingService`. Для контроллера/интерцептора — по возможности не тестировать сам `multer` (это библиотека), тестировать только код, который пишется поверх (guard доступа, обработчик `MulterError`).
- **E2e (api, `supertest`).** Загрузка файла через `supertest`: `.post('/meetings/:id/files').attach('file', buffer, 'name.ext')` — стандартный паттерн `supertest` для multipart, не требует реального файла на диске тестового окружения (можно `Buffer.from('...')`). Для проверки «побайтового совпадения» при скачивании — сравнивать `Buffer` загруженного и полученного тела ответа (`response.body` как `Buffer при `responseType('blob')`/`buffer()`). Тестовая директория хранения — отдельный env/`MEETING_FILES_DIR`для e2e (например, во временную директорию ОС), чтобы не засорять`apps/api/storage`при прогонах и не конфликтовать с dev-данными; очищать после набора тестов, аналогично тому, как e2e для meetings/users не чистят БД (см.`apps/api/CLAUDE.md`, раздел «Тесты») — но файлы на диске, в отличие от строк в dev-БД, стоит зачищать, чтобы не накапливать мусор в репозитории/контейнере CI.
- **Playwright MCP (фазы 3–4, web).** Загрузка небольшого тестового файла из `test`-фикстуры через `browser_file_upload`; проверка прогресса потребует либо намеренно медленного/большого файла в дев-окружении, либо проверки самого факта показа индикатора (наличие элемента), а не покадровой анимации.

## 9. Безопасность

- **Path traversal.** Никогда не строить путь на диске из `file.originalname` или из пользовательского `fileId`/`meetingId` без валидации (тот факт, что `meetingId`/`fileId` — `uuid` из Prisma, уже снижает риск, если проверять их формат перед использованием в пути).
- **MIME по декларации клиента ненадёжен.** `file.mimetype`, который присылает браузер, — это то, что указал клиент, а не результат анализа содержимого. Поскольку PRD сознательно не ограничивает типы файлов, здесь это не блокер, но стоит помнить при выводе `mimeType` в UI/при скачивании — не использовать его как единственный сигнал безопасности (например, при показе файла напрямую в браузере, чего PRD explicitly не требует — «не в скоупе»).
- **Отдача файла с `Content-Disposition: attachment`** (а не `inline`) — обязательна, чтобы браузер не пытался исполнить/отрендерить произвольный загруженный файл (например, `.html` от одного участника, открытый другим) в контексте origin API.
- **Лимит на количество/параллельность загрузок** — вне скоупа PRD (нет квот), но стоит держать в уме: без лимита на количество файлов на встречу пользователь может залить очень много файлов до общего лимита размера ФС — не блокирующая проблема для MVP, но кандидат в «не в скоупе» риски.

## 10. Сводка решений по фазам плана

| Фаза | Технические решения                                                                                                                                                                                                                                             |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `MeetingFile` в Prisma; `MEETING_FILES_DIR`/`MEETING_FILE_MAX_SIZE_BYTES` в `.env`/`.env.example`; `FileInterceptor` + `diskStorage` + `multer.limits.fileSize`; guard проверки владения до записи на диск; обработка `MulterError` → 400 с понятным сообщением |
| 2    | `StreamableFile` + `fs.createReadStream` для скачивания; доступ участников — сопоставление `user.email` с `meeting.participants` (см. §4, зафиксировать как решение, не додумывать в коде); удаление — сначала БД, потом `fs.unlink` (ENOENT игнорировать)      |
